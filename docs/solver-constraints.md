# Ограничения солвера (OR-Tools / CP-SAT)

Живой документ: что солвер **обязан** соблюдать и что лишь **предпочитает**.  
Код: `mvp_1.py` → `solve_schedule`. Задачи: [TZ-solver.md](TZ-solver.md). Вход JSON: [TZ-parser.md](TZ-parser.md).

При изменении ограничений в коде обновляйте этот файл в том же изменении.

Статусы: **готово** · **частично** · **в планах**

---

## Как устроена модель

Солвер выбирает для каждого занятия одно размещение:

> «это занятие начинается в таком-то слоте, в такой-то аудитории»

Если занятие длинное (`duration_slots > 1`), одним выбором оно занимает **несколько подряд идущих слотов** того же дня (например, 3-я и 4-я пара). Аудитория, преподаватель и группа считаются занятыми на **весь** этот интервал.

До того как запускается OR-Tools, многие невозможные варианты просто **не попадают в список кандидатов** (не создаётся переменная). Это тоже ограничения — просто они отсекаются заранее.

На больших входах (`solve_strategy=auto` / `two_phase`) сначала назначаются **слоты**, затем **аудитории**; домен аудиторий дополнительно режется до `max_candidate_rooms`.

## Жёсткие правила (нарушать нельзя)

### 1. Каждое занятие ставится ровно один раз — **готово**

Нельзя «забыть» пару и нельзя поставить её дважды. Ровно одно размещение: один старт + одна аудитория (или виртуальная площадка).

### 2. Аудитория не делится в один момент — **готово**

В одной физической аудитории ИЕНИМ в один таймслот не может идти два занятия, **если у них пересекаются недели** семестра.

- Чётная и нечётная неделя в одной аудитории и слоте — можно.
- Два занятия «каждую неделю» в одной аудитории и слоте — нельзя.
- Онлайн / внешняя площадка / спортзал **не конкурируют** за аудитории ИЕНИМ между собой и с очными парами.

### 3. Преподаватель не раздваивается — **готово**

Один и тот же преподаватель не ведёт два занятия в одном слоте при пересечении недель.

- Если на пару записаны двое (совместное ведение) — **оба** заняты этим слотом.
- Подгруппы с разными преподавателями могут идти параллельно.
- Пустое ФИО не «освобождает» слот: подставляется **уникальный** placeholder `UNKNOWN:{course_id}` (или `:sgN`), он участвует в конфликте как обычный преподаватель.
- Режим `missing_teacher_policy=strict` (или `strict=true`): очные без преподавателя → ошибка, solve не запускается; online/sport — placeholder.

### 4. Академическая группа не раздваивается — **готово**

Одна группа не может быть на двух парах в одном слоте при пересечении недель.  
Разные половины потока (разные `group_ids`) — могут идти одновременно.

### 5. Недели учитываются при любом конфликте — **готово**

Конфликт аудитории / преподавателя / группы срабатывает **только если множества недель пересекаются**.

Поддерживаются паттерны: все недели, нечёт / чёт, диапазон (`2–9`), явный список недель.

### 6. Длинные занятия — непрерывный блок — **готово**

Лаба на два слота занимает два **соседних** слота одного дня одним размещением.  
Дробный `duration_slots` из парсера (например `1.5`) приводится к целому через **ceil** при expand (`1.5` → `2`).  
По умолчанию блок **не перескакивает через обед** (между 2-й и 3-й парой). Разрешить разрыв через обед можно конфигом `allow_duration_across_lunch`.

### 7. Закреплённое расписание (`fixed_schedules`) — **готово**

Если курсу заранее заданы слоты — занятие может стоять только в них, и каждый указанный слот должен быть реально занят этим курсом.  
Число слотов должно сходиться с числом занятий × длительностью. Битый ввод отсекается до запуска солвера.

### 8. Онлайн / НТК / внешняя площадка / спортзал — **готово**

Такие занятия **не получают** обычный `room_id` вроде `304`. Им выделяется служебная площадка (`__ONLINE__:…`, `__EXTERNAL__:…` и т.п.).

Очные курсы эти служебные id не используют.  
Конфликты преподавателя и группы для онлайн всё равно действуют.

### 9. Та же аудитория, что у связанной лекции — **готово**

Поле `same_room_as_course_id` («вместе с лекциями»): практика/лаба и связанный курс (все их очные занятия) получают **один и тот же** `room_id`. Онлайн-занятия в связь не входят.

## Что отсекается ещё до солвера

Эти условия не дают даже рассмотреть плохой вариант:

| Правило | Статус | Простыми словами |
|---------|--------|------------------|
| Вместимость | готово | В аудиторию должно помещаться нужное число студентов |
| Оснащение | готово | Есть нужная доска / ПО / прочие hard-требования |
| Запреты преподавателя | готово | Слот из «не могу» не предлагается (для длинной пары — ни один слот блока) |
| Fixed-слоты | готово | Вне закреплённых слотов вариантов нет |
| Fixed-аудитория из анкеты | готово | Если однозначно указана аудитория — только она |
| Online / external / sport | готово | В домене только виртуальная площадка, не справочник ИЕНИМ |
| Список разрешённых аудиторий | готово | `allowed_room_ids` — только эти аудитории ИЕНИМ |
| Занятые заранее аудитории | готово | `room_preblocked` — слот+ауд из эталона не предлагаются |
| Hard-правила из пожеланий дисциплин | готово | `time_wishes` + адаптер `time_wish_rules` → канон (`no_day` / `forbid_slots` / `no_slot_after` / `no_slot_before` / `day_part`); soft=false жёстко, soft=true в objective; unmanaged → warning |

Если после отсечения вариантов не осталось — солвер сразу возвращает ошибку с кодом (`NO_FEASIBLE_ROOM`, `FIXED_SCHEDULE_NO_DOMAIN`, `DURATION_NO_BLOCK`, `EMPTY_PLACEMENT_DOMAIN`, …), не запуская бессмысленный поиск.

## Диагностика ответа — **готово**

Единый контракт неуспеха и предупреждений:

| Статус | Когда | Что в ответе |
|--------|-------|----------------|
| `ERROR` | Pre-check / битый ввод / пустой домен до CP-SAT | Непустой `errors[]` с `code`, часто `hints` |
| `NO_SOLUTION` | CP-SAT (mono / phase1 / phase2) не нашёл допустимое | `errors[]` с `NO_SOLUTION` / `PHASE*_NO_SOLUTION` / `SOLVER_TIMEOUT` + `hints` |
| `SUCCESS` | Решение есть, soft и прочие warnings пусты | `errors: []`, `schedule` |
| `SUCCESS_WITH_WARNINGS` | Решение есть, но есть warnings | Soft-невыполнения (`UNMET_WANTED_SLOT`, `SCHEDULED_ON_SATURDAY`, …) и/или placeholder-преподаватели |

Pre-check (`precheck_placement_domains`) гоняет каждый instance до запуска солвера.  
`diagnose_no_solution` добавляет подсказки (fixed, запреты, загруженные teachers/groups, timeout).  
`collect_unmet_soft_warnings` поднимает невыполненные soft в `warnings[]` без смены допустимости.

## Мягкие предпочтения (желательно, но не обязательно)

Солвер **максимизирует** сумму бонусов и штрафов. Решение всегда обязано быть допустимым по жёстким правилам; soft только выбирает «лучшее» среди допустимых.

| Предпочтение | Статус | Смысл |
|--------------|--------|--------|
| Желаемые слоты преподавателя | готово | Бонус, если старт пары попал в указанные в анкете слоты |
| Предпочтительная вместимость | готово | Штраф, если аудитория меньше желаемой из анкеты |
| Предпочтительный тип аудитории | готово | Штраф за несовпадение вида (лекционная / компьютерный и т.п.) |
| Окна у группы | готово | Штраф за пустой слот между первой и последней парой группы в дне |
| Поздние пары / суббота | готово | Штраф за `slot_index >= late_slot_from` и за субботу |
| Пожелания из листа дисциплин | готово | Soft `prefer_slots` / `strength=soft`; сырой текст → warning |

Веса в `config`; `0` отключает терм. По умолчанию желаемый слот важнее типа/вместимости.

## Настройки, которые меняют поведение

- **Время поиска** — `max_time_in_seconds` (по умолчанию 10 с; полный прогон 300–900), `num_search_workers`.
- **Масштаб** — `solve_strategy` (`auto`/`monolithic`/`two_phase`), `max_candidate_rooms`, `var_threshold_two_phase`, `repair_on_two_phase_fail`, `scope_course_ids`.
- **Веса soft** — `weight_wanted_slot`, `weight_preferred_capacity`, `weight_preferred_room_type`, `weight_time_wish`, `weight_group_gap`, `weight_late_slot`, `weight_saturday`.
- **Поздние пары** — `late_slot_from` (по умолчанию 5).
- **Оценка числа студентов**, если парсер не дал точное — `default_group_size`, для лекций потока ещё `lecture_stream_size_factor`.
- **Календарь недель** — `semester_weeks` / `semester_week_start` (по умолчанию недели 1…16).
- **Обед и длинные пары** — `lunch_break_after_slot_index` (обычно 2), `allow_duration_across_lunch` (по умолчанию нельзя).
- **Нет преподавателя** — `missing_teacher_policy` (`placeholder` \| `strict`), либо общий флаг `strict`.
- **Стык с «грязными» данными (п.13.2)** — `fixed_schedule_mismatch_policy`, `infeasible_fixed_room_policy`, `unplaceable_instance_policy` (`strict` \| `warn`). В `warn`: пропускаем битый fixed / невместимый `fixed_room` / instance без аудитории → warnings `FIXED_SCHEDULE_COUNT_MISMATCH` / `INFEASIBLE_FIXED_ROOM_IGNORED` / `UNPLACEABLE_INSTANCE_DROPPED`.

## Что из входного JSON на что влияет

- **Вместимость и флаги аудиторий** → помещается ли группа, хватает ли оснащения  
- **Требования курса / ПО** → какие аудитории вообще рассматриваются  
- **Запреты преподавателя** → какие слоты вычеркнуты  
- **Анкетные пожелания** → фиксированная аудитория (жёстко) + желаемые слоты/тип (мягко)  
- **fixed_schedules** → жёсткая привязка к слотам  
- **Преподаватели и группы на занятии** → конфликты «человек не в двух местах»  
- **week_pattern** → когда два занятия реально сталкиваются  
- **duration_slots** → сколько слотов подряд занимает одно размещение  
- **venue_type / needs_room** → нужна ли аудитория ИЕНИМ или виртуальная площадка  
- **allowed_room_ids** → whitelist аудиторий  
- **same_room_as_course_id** → одна аудитория на связанную пару лекция/практика  
- **room_preblocked** → занятые заранее слот+ауд не используются  
- **time_wishes / time_wish_raw** → hard/soft ограничения по времени; сырой текст → warning

## Как поддерживать документ

1. Новое правило в коде → короткое описание здесь: что нельзя / что желательно, статус.  
2. Явно писать: жёсткое или мягкое.  
3. Помнить про недели и длинные блоки: конфликт почти всегда «на каждый слот блока + при пересечении недель».  
4. Новый код ошибки при пустом домене — упомянуть в разделе «до солвера».  
5. Закрыли пункт в [TZ-solver.md](TZ-solver.md) — здесь статус **готово**.
