# Схема `courses[].instances` (парсер → солвер)

Документ фиксирует структуру данных, которую `parser/importer.py` формирует для солвера
после интеграции пунктов 3 (подгруппы/команды), 4 (несколько преподавателей в ячейке),
5 (канонический `teacher_id`), 6 (связка анкеты), 7 (аудитории и требования),
8 (место проведения), 9 (`venue_type`), 10 (пожелания по времени),
11 (комментарии) и 12 (`fixed_schedules` для физкультуры).

**Статус:** реализовано в `parser/importer.py` (`_parse_subgroup_counts`,
`_parse_teacher_cell`, `_build_course_instances`, `_finalize_teacher_ids`,
`_link_desires_to_courses`, `_parse_rooms`, `_parse_requirements`,
`_parse_location`, `_resolve_same_room_links`, `_classify_venue`,
`_parse_comments_hints`, `_finalize_time_wishes`, `_parse_pe_slots`,
`_generate_fixed_schedules`, `_validate_fixed_schedules`,
`_finalize_course_instances`).
`mvp_1.py` не изменялся; поля `courses[].name` и `courses[].teacher_id` удалены,
поэтому потребителю нужна отдельная адаптация (см. §9).

---

## 1. Общая идея

Одна строка Excel и один тип занятия по-прежнему дают один объект `courses[]` — **курс**.
Но внутри курса теперь лежит список `instances` — конкретных занятий, которые нужно поставить
в расписание. Если деления нет, у курса ровно один instance (`subgroup_count = 1`).

```
courses[]                       # нагрузка: дисциплина + тип занятия
└── instances[]                 # единица планирования для солвера
```

Причины появления нескольких instances:

- в колонке «Кол-во подгрупп…» указано число > 1;
- в ячейке ФИО есть маркер команды/подгруппы (`2 команды`, `(2 п/гр)`, `3 группы`);
- в ячейке есть общий префикс (`2 подгруппы:`, `по одной подгруппе каждому`).

Все поля базового курса сохранены для обратной совместимости с текущим солвером.

## 2. Схема курса (`courses[]`)

```json
{
  "id": "c42",
  "discipline": "Математика",
  "lesson_type": "практика",
  "teacher_ids": ["Нагребецкая Ю.В.", "Перминова О.Е.", "Расин О.В."],
  "group_ids": ["МЕН-160409", "МЕН-162401"],
  "lessons_per_week": 1,
  "week_pattern": "weekly",
  "duration_slots": 1.0,
  "requirements": ["screen", "software"],
  "needs_software": true,
  "software_raw": "Excel",
  "location_raw": "403, 405",
  "allowed_room_ids": ["403", "405"],
  "venue_type": "room",
  "time_wish_raw": "Не ставить в субботу, желательно первая половина дня",
  "time_wish_rules": [ ... ],
  "time_wish_unmanaged": [],
  "comments_raw": "Практики сдвоенные пары",
  "comments_hints": [ ... ],
  "same_room_as_course_id": null,
  "students_needed": 60,
  "subgroup_count": 5,
  "subgroup_column_count": 5,
  "subgroup_raw": "5",
  "instances": [ ... ]
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | string | Идентификатор курса, `c<N>` |
| `discipline` | string | Название дисциплины без типа занятия (нормализованные пробелы) |
| `lesson_type` | string | `лекция` \| `практика` \| `лабораторная` |
| `teacher_ids` | string[] | Все уникальные преподаватели курса (канонические `Фамилия И.О.`) |
| `group_ids` | string[] | Все группы строки Excel (не подгруппы!) |
| `lessons_per_week` | int | Число занятий в неделю по правилам часов, см. §20 |
| `week_pattern` | string | `weekly` \| `odd` \| `even`, см. §20 |
| `duration_slots` | number | Длительность занятия в слотах (1, 1.5, 2), см. §20 |
| `requirements` | string[] | Оснащение, см. §14 |
| `needs_software` | bool | `true`, если в «ПО на практики, лаборатории» задано ПО |
| `software_raw` | string \| null | Сырое значение колонки ПО |
| `location_raw` | string \| null | Сырое «Где проводятся практики, лаборатории?» |
| `allowed_room_ids` | string[] | Найденные в справочнике номера аудиторий |
| `venue_type` | string | `room` \| `online` \| `external` \| `unspecified`, см. §16 |
| `time_wish_raw` | string \| null | Сырая колонка пожеланий по времени (сохраняется всегда) |
| `time_wish_rules` | object[] | Формализованные правила, см. §17 |
| `time_wish_unmanaged` | object[] | Нераспознанные фрагменты пожеланий, см. §17 |
| `comments_raw` | string \| null | Сырая колонка «Комментарий, особенности дисциплины» |
| `comments_hints` | object[] | Эвристики из комментария, см. §18 |
| `same_room_as_course_id` | string \| null | Лекционный курс, с которым совмещено место, см. §15 |
| `students_needed` | number | Сумма `size` всех `group_ids` (после `_finalize_group_sizes`) |
| `subgroup_count` | int | Итоговое число instances (`N`), `>= 1` |
| `subgroup_column_count` | int | Число подгрупп, распознанное из колонки Excel для этого типа занятия |
| `subgroup_raw` | string \| null | Сырое значение колонки подгрупп (сохраняется всегда) |
| `instances` | object[] | Список занятий, см. ниже |

Служебное поле `_course_number` (`row["Курс"]`) используется при сборке и в итоговый JSON не попадает.
Поля `name` и `teacher_id` из курса удалены: отображаемое имя собирается как
`<discipline> (<lesson_type>)`, преподаватели берутся из `teacher_ids`.

## 3. Схема instance (`courses[].instances[]`)

```json
{
  "id": "c42_i3",
  "course_id": "c42",
  "name": "Математика (практика), подгруппа 3/5",
  "lesson_type": "практика",
  "lesson_kind": "practice_subgroup",
  "teacher_ids": ["Расин О.В."],
  "group_ids": ["МЕН-160409", "МЕН-162401"],
  "students_needed": 12,
  "subgroup_index": 3,
  "subgroup_count": 5,
  "team_label": null,
  "team_count": null,
  "team_index": null,
  "lessons_per_week": 1,
  "week_pattern": "weekly",
  "duration_slots": 1.0,
  "requirements": ["screen", "software"],
  "needs_software": true,
  "software_raw": "Excel",
  "location_raw": "403, 405",
  "allowed_room_ids": ["403", "405"],
  "venue_type": "room",
  "time_wish_raw": "Не ставить в субботу, желательно первая половина дня",
  "time_wish_rules": [ ... ],
  "time_wish_unmanaged": [],
  "comments_raw": "Практики сдвоенные пары",
  "comments_hints": [ ... ],
  "same_room_as_course_id": null,
  "same_room_as_instance_ids": []
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | string | `<course_id>_i<subgroup_index>` |
| `course_id` | string | Ссылка на курс |
| `name` | string | Имя с суффиксом подгруппы или маркера команды |
| `lesson_type` | string | Дублирует тип занятия курса |
| `lesson_kind` | string | Классификация, см. §4 |
| `teacher_ids` | string[] | Преподаватели именно этого instance (может быть несколько при co-teaching) |
| `group_ids` | string[] | **Полный** список групп курса (см. §9) |
| `students_needed` | number | `max(1, ceil(students_needed курса / subgroup_count))` |
| `subgroup_index` | int | Номер instance, `1..N` |
| `subgroup_count` | int | Всего instances у курса (`N`) |
| `team_label` | string \| null | Сырой маркер: `"2 команды"`, `"2 п/гр"`, `"3 группы"` |
| `team_count` | int \| null | Число команд/подгрупп из маркера преподавателя |
| `team_index` | int \| null | Номер команды внутри серии преподавателя (1..`team_count`) |
| `lessons_per_week` | int | Копия числа занятий в неделю курса, см. §20 |
| `week_pattern` | string | Копия `week_pattern` курса, см. §20 |
| `duration_slots` | number | Копия длительности занятия курса, см. §20 |
| `requirements` | string[] | Копия требований курса, см. §14 |
| `needs_software`, `software_raw` | bool, string \| null | Копия полей курса |
| `location_raw` | string \| null | Копия сырого места проведения |
| `allowed_room_ids` | string[] | Копия списка аудиторий курса |
| `venue_type` | string | Копия типа площадки курса, см. §16 |
| `time_wish_raw` | string \| null | Копия сырых пожеланий курса |
| `time_wish_rules` | object[] | Только правила `scope=course` и правила своих преподавателей, см. §17 |
| `time_wish_unmanaged` | object[] | Копия нераспознанных фрагментов курса |
| `comments_raw` | string \| null | Копия сырого комментария курса |
| `comments_hints` | object[] | Только hints, подходящие по `scope` к типу занятия, см. §18 |
| `same_room_as_course_id` | string \| null | Лекционный курс для совмещённого места |
| `same_room_as_instance_ids` | string[] | Конкретные лекционные instances того же потока |

Инварианты (проверяются `_validate_course_instances`, нарушения → `warnings`):

- `len(instances) == course.subgroup_count`;
- `subgroup_index` образуют последовательность `1..N`;
- все `teacher_ids` присутствуют в глобальном `teachers`;
- `students_needed >= 1`.

## 4. `lesson_kind`

| Значение | Когда выставляется |
|----------|--------------------|
| `lecture_stream` | Лекция без деления (вариант А): один instance, все ФИО в `teacher_ids` |
| `lecture_team` | Лекция, но есть явный маркер команд/подгрупп (маркер важнее типа занятия) |
| `co_taught` | Практика/лаба с несколькими ФИО и **без** признаков деления — один instance |
| `single` | Один преподаватель, деления нет |
| `practice_subgroup` | Практика, разделённая на подгруппы/команды (вариант Б) |
| `lab_subgroup` | Лабораторная, разделённая на подгруппы/команды (вариант Б) |

## 5. Алгоритм: колонка подгрупп

`_parse_subgroup_counts(raw)` → `{practice, laboratory, raw, ambiguous, zero, unparsed, extra}`.

1. Пусто/`NaN` → оба `None`, без предупреждения.
2. Нормализация: NBSP, схлопывание пробелов; разбиение по `\n` и `;`.
3. В строке ищется тип: `лаб…` → лабораторная, `пр…`/`практ…` → практика.
4. Берётся **ведущее число строки** (`^\s*(\d+)`), а не все числа: иначе номера групп
   в скобках (`3 ВМиКН (МЕН-340101, …)`) дадут мусор.
5. Типизированные строки (`6 (пр.)`, `11 (лаб.)`) имеют приоритет.
6. Если типизированных строк нет:
   - одно число (`5`, `10 +`, `2пс`) → применяется к практике и лабораторным;
   - несколько строк с текстовыми категориями (`1 ФиНХ\n1 ДФиПХ`) — это отдельные
     популяции, их числа **суммируются**;
   - несколько «голых» чисел (`5\n3`, `2\n\n5 (?)`) → первое = практика,
     последнее = лабораторные, плюс `warnings` о неоднозначности.
7. `0` → `warnings`, трактуется как отсутствие деления (`1`).
8. Если распознан только один тип, второй получает `1` + `warnings`.
9. Неразобранный текст сохраняется в `extra`/`unparsed` и попадает в `warnings`;
   уже распознанные значения не теряются.
10. `subgroup_raw` сохраняется у курса всегда.

Для типа занятия: лекция всегда `column_count = 1`, практика берёт `practice`,
лабораторная — `laboratory`.

## 6. Алгоритм: ячейка ФИО и маркеры

`_parse_teacher_cell(raw)` → `(specs, meta)`, где
`specs = [{name, team_label, team_count}, …]`, `meta = {cell_hint, cell_label, unparsed, unresolved, raw}`.

1. Ячейка режется на сегменты по `,`, `;`, переводам строк, `+`, ` или ` и одиночному `/`
   (слэш внутри `п/гр` не считается разделителем).
2. В каждом сегменте ищутся все ФИО в поддерживаемых форматах:
   - `Фамилия И.О.` / `Фамилия И.О` / `Фамилия И. О.`;
   - `Фамилия ИО` / `Фамилия И О` — инициалы без точек;
   - `И.О. Фамилия` — инициалы перед фамилией;
   - полное ФИО `Фамилия Имя Отчество`, если сокращённых форм в сегменте нет
     (канонизация полных и кратких форм — п.5 ТЗ, отдельный шаг).
3. Нормализация:
   - схлопывание пробелов и удаление окружающей пунктуации;
   - склейка `Д. Р.` → `Д.Р.`;
   - инициалы без точек приводятся к `Фамилия И.О.`;
   - `И.О. Фамилия` переставляется в `Фамилия И.О.`;
   - латинские буквы-двойники в фамилии заменяются кириллическими
     (`Cосновских` → `Сосновских`);
   - финальная точка в инициалах сохраняется, если была в источнике.
4. Маркер ищется в том же сегменте:
   - `N команд`, `N подгрупп`, `N подгр`, `N п/гр`, `N групп`;
   - одиночное `(N)` рядом с ФИО (`Алябышева И.В. (3)`);
   - глобальные фразы `по одной подгруппе каждому`, `у каждого по N группы` —
     применяются ко всем ФИО ячейки.
5. Сегмент без ФИО, но с числом (`2 подгруппы:`) → `cell_hint` для всего занятия.
6. Несколько ФИО в одном сегменте с одним маркером → маркер применяется ко всем
   (с `warnings` о неоднозначности).
7. Непустая ячейка без ФИО → `warnings`, курс не падает.
8. Все имена курса и instances регистрируются в глобальном `teachers`.
   `_split_teacher_names` переиспользует этот парсер и отдаёт очищенные имена анкете `table3`.

Примеры очистки:

| Вход | `name` | `team_label` |
|------|--------|--------------|
| `Коврижных О.О.-2 команды` | `Коврижных О.О.` | `2 команды` |
| `Буянова Е.С.(2 п/гр)` | `Буянова Е.С.` | `2 п/гр` |
| `Кувшинов Д. Р.` | `Кувшинов Д.Р.` | — |
| `Соколовский ДН` | `Соколовский Д.Н.` | — |
| `Д.С. Незнахин` | `Незнахин Д.С.` | — |
| `Cосновских В.Я.` | `Сосновских В.Я.` | — |
| `Студенок С.И. (по одной подгруппе каждому)` | `Студенок С.И.` | `по одной подгруппе каждому` |

## 7. Классификация А / Б

Для каждого типа занятия отдельно:

- `teacher_count` — число найденных ФИО;
- `column_count` — число подгрупп из колонки (лекция → 1);
- `cell_hint` — префиксный маркер ячейки;
- `expanded` — ФИО, развёрнутые по `team_count` (преподаватель с `2 команды` даёт 2 записи);
- `split_requested = len(expanded) > 1 or cell_hint > 1 or (не лекция и column_count > 1)`.

### Вариант А — `split_requested = false`

Один instance:

- `teacher_ids` — все уникальные ФИО;
- `subgroup_index = 1`, `subgroup_count = 1`;
- `lesson_kind`:
  - лекция → `lecture_stream`;
  - несколько ФИО на практике/лабе → `co_taught` + информационный `warnings`;
  - одно ФИО → `single`.

### Вариант Б — `split_requested = true`

1. `N = max(1, column_count, cell_hint, len(expanded), teacher_count)`.
2. Если есть явные маркеры, каждый преподаватель разворачивается в `team_count` записей
   с `team_index = 1..team_count`.
3. Если развёрнутых записей меньше `N` — недостающие добираются циклическим повторением
   преподавателей, в `warnings` пишется нехватка.
4. Если преподавателей больше `N` — они делятся на `N` сбалансированных непрерывных групп
   (например, 5 ФИО / 4 подгруппы → `[2, 1, 1, 1]`); внутри instance `teacher_ids` может быть несколько.
5. Если преподавателей меньше `N` — циклическое повторение + `warnings`.
6. `subgroup_index = 1..N`, `subgroup_count = N`.
7. `lesson_kind` = `lecture_team` / `practice_subgroup` / `lab_subgroup`.
8. Явные маркеры команд приоритетнее числа из колонки; при расхождении — `warnings`.

Примеры:

- «Математика», 5 подгрупп, 5 ФИО → 5 instances по одному преподавателю.
- «Информационные технологии», `-2 команды / -4 команды / -1 команда` → 7 instances.
- Лекция `2 подгруппы: Репницкий, Маслова` → 2 instances `lecture_team`.
- Лекция с двумя ФИО без маркеров → 1 instance `lecture_stream` с двумя `teacher_ids`.

## 8. `students_needed`

- `_finalize_group_sizes` выполняется первой и заполняет `groups[].size`
  (реальное число или `default_group_size` + `warnings`).
- `_finalize_course_instances` затем выставляет:
  - `course.students_needed = Σ size(group_ids)`;
  - `instance.students_needed = max(1, ceil(course.students_needed / subgroup_count))`.

Значение приблизительное: подгруппы считаются равными, даже если в тексте указаны
явные списки групп для конкретных популяций.

## 9. Ограничения и следующий шаг

1. **`group_ids` у всех instances полные.** Явные списки групп из текста подгрупп
   (`3 ВМиКН (МЕН-340101, 340102)`, `МЕН-251101: практика - …`) сохраняются только
   в `subgroup_raw`/`warnings`; точное сопоставление instance ↔ группа — отдельный шаг.
2. **`students_needed` делится поровну**, а не по фактическим размерам подгрупп.
3. **`mvp_1.py` не изменён** и всё ещё читает legacy-поля
   `hours_per_semester` и `courses[].teacher_id`; после их удаления он получит
   `lessons_per_week = 1` и не сможет прочитать преподавателя. Совместимость с
   `lessons_per_week` / `teacher_ids` из JSON — отдельный шаг.
4. Сессия, `week_pattern`, 7-я пара, `room_preblocked` и политика пустых ФИО
   реализованы — см. §20–§24. `location_raw` и `comments_hints.week_ranges`
   сохраняются для будущего шага.
5. Канонизация ФИО (п.5), связка анкеты (п.6), аудитории/требования (п.7), место
   проведения (п.8), `venue_type` (п.9), пожелания по времени (п.10), комментарии
   (п.11), физкультура/fixed-слоты (п.12), сессия (п.13), 7-я пара (п.14),
   занятость аудиторий (п.15), часы (п.16) и курсы без преподавателя (п.17)
   реализованы — см. §11–§24.

## 10. Предупреждения (`warnings`)

Все аномалии попадают в общий список строками с контекстом «лист + id курса + сырое значение»:

- неразобранные/неоднозначные подгруппы, `0`, лишний текст;
- несовпадение `column_count` и числа instances из маркеров;
- ячейка ФИО непустая, но ФИО не найдено;
- неразобранные фрагменты ФИО (`кто-то еще (обсуждается)`);
- несколько ФИО без маркера деления → `co_taught`;
- нехватка/избыток преподавателей относительно `N`;
- несколько разных маркеров в одном instance;
- ошибки финальной валидации instances;
- `venue_type=unspecified`: `НТК='НК'` или нераспознанное место;
- `unmanaged_wish:` — нераспознанное пожелание по времени с причиной;
- `comments_hint:` — извлечённая эвристика (длительность, недели, период);
- `venue_conflict:` — комментарий говорит об онлайне, но `venue_type` очный;
- `fixed_schedules:` / `time_slots:` — фатальные ошибки валидации (см. §19).

## 11. Канонический `teacher_id` (п.5 ТЗ)

`_finalize_teacher_ids` выполняется после парсинга нагрузки и анкеты и переписывает
все ссылки в `courses[].teacher_ids`, `instances[].teacher_ids`,
`teachers_impossible_slots[].teacher_id`, `teachers_wanted_slots[].teacher_id`.

### 11.1. Формат

```
teacher_id = "<Фамилия> <И.О.>"
```

Примеры:

| Источник | `teacher_id` |
|----------|--------------|
| `Щапов Владислав Анатольевич` | `Щапов В.А.` |
| `Щапов В.А.` / `Щапов В. А.` | `Щапов В.А.` |
| `Киселев Е.А` / `Киселев Е.А.` | `Киселев Е.А.` |
| `Бострем И.` + `Бострем И.Г.` | `Бострем И.Г.` |
| `Валдайских В.` + `Валдайских В.В.` | `Валдайских В.В.` |
| `Владимир Савельев` | `Савельев В.` |

В `teachers[]` **не добавляются** `aliases`: остаётся только `{"id": "<канонический id>"}`.

### 11.2. Алгоритм

1. ФИО приводится к виду `Фамилия И.О.` тем же нормализатором, что и в §6
   (пробелы, точки, латинские буквы-двойники, `И.О. Фамилия`).
2. Строка разбирается в `(фамилия, кортеж инициалов)`:
   - `Фамилия И.О.` / `Фамилия И.О` → `("Фамилия", ("И", "О"))`;
   - `Фамилия И.` → `("Фамилия", ("И",))`;
   - `Фамилия Имя Отчество` → первые буквы имени и отчества;
   - `Фамилия Имя` → одна буква;
   - `Имя Фамилия` определяется по окончанию фамилии (`-ов`, `-ев`, `-ин`, `-ский`,
     `-ая`, `-ко`, …).
3. Одинаковые `(фамилия, инициалы)` схлопываются в один id.
4. Форма с одним инициалом объединяется с более полной формой той же фамилии,
   если кандидат **ровно один**:
   `Бострем И.` + `Бострем И.Г.` → `Бострем И.Г.`.
5. Если кандидатов несколько, объединения нет; пишется `warning`.
6. Неразобранное ФИО сохраняется как есть и попадает в `warnings`.
7. Факт объединения вариантов пишется в `warnings` (например, `'Бострем И.'` →
   `'Бострем И.Г.'`).

`teachers[]` пересобирается по каноническим id; все ссылки в курсах и анкете
проверяются финальной валидацией instances.

## 12. Связка анкеты с `course_id` (п.6 ТЗ)

Поля добавлены в **оба** списка: `teachers_impossible_slots[]` и
`teachers_wanted_slots[]`. Существующие `teacher_id`, `course_name`, `group_ids`,
`timeslots_ids`, `comments` остаются для fallback солвера.

```json
{
  "teacher_id": "Щапов В.А.",
  "course_id": "c17",
  "course_ids": ["c17"],
  "instance_ids": ["c17_i1"],
  "match_type": "exact",
  "course_name": "Математика (лекция)",
  "group_ids": ["МЕН-160409"]
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `course_id` | string \| null | Единственный найденный курс; `null` при неоднозначности/отсутствии |
| `course_ids` | string[] | Все подходящие курсы (для fallback/диагностики) |
| `instance_ids` | string[] | Instances найденного курса с этим преподавателем (или все instances курса) |
| `match_type` | string | `exact` \| `ambiguous` \| `no_group_overlap` \| `none` |

### 12.1. Алгоритм

1. Из `course_name` берётся тип занятия (`(лекция)` / `(практика)` / `(лабораторная)`).
2. Дисциплина нормализуется: нижний регистр, `ё → е`, NBSP/табы/переносы → пробел,
   удаление хвостового `(тип занятия)`, схлопывание тире и пробелов.
3. Ищутся курсы с тем же `lesson_type` и нормализованной дисциплиной.
4. Среди них остаются курсы, где `teacher_id` входит в `teacher_ids` курса или
   любого его instance.
5. Проверяется пересечение нормализованных `group_ids` (регистр и пробелы не важны).
6. Результат:
   - один курс → `match_type="exact"`, `course_id` заполнен;
   - несколько → `ambiguous`, `course_id=null`, `course_ids` заполнен, `warning`;
   - преподаватель+дисциплина совпали, группы — нет → `no_group_overlap`, `warning`;
   - ничего не найдено → `none`, `warning`.

На текущих данных `table3.xlsx` все 331 строка получают `match_type="exact"`.

## 15. Место проведения (п.8 ТЗ)

Источник — «Где проводятся практики, лаборатории?». Сырой текст сохраняется всегда
в `location_raw`; поля добавляются и на курс, и на instances.

```json
{
  "location_raw": "там же, где лекции + ауд. 311, 312",
  "allowed_room_ids": ["311", "312"],
  "same_room_as_course_id": "c17",
  "same_room_as_instance_ids": ["c17_i1"]
}
```

| Поле | Уровень | Описание |
|------|---------|----------|
| `location_raw` | курс + instance | Исходный текст без потери информации |
| `allowed_room_ids` | курс + instance | Номера, найденные в справочнике `rooms[]` |
| `same_room_as_course_id` | курс + instance | Лекционный курс того же потока |
| `same_room_as_instance_ids` | instance | Конкретные лекционные instances (может быть несколько) |

### 15.1. Номера аудиторий

1. Регулярка ищет `3`-значные номера с необязательным корпусом/литерой:
   `202а`, `358 в`, `266/1`, `462а`.
2. Пробел внутри номера убирается (`358 в` → `358в`).
3. Номер сверяется с `rooms[].id`.
4. Найденные номера попадают в `allowed_room_ids` без дублей.
5. Ненайденные номера **не** создают отдельного поля (`unknown_room_refs` отсутствует):
   они перечисляются в `warnings`, а исходный текст остаётся в `location_raw`.

Пример: `"403, 405"` → `allowed_room_ids=["403","405"]`.

### 15.2. «Вместе с лекциями»

Маркеры: `вместе с лекциями`, `там же, где и лекции`, `там же где и лекции`,
`как и лекции`, `где и лекция`, `практика - как и лекции`.

Алгоритм `_resolve_same_room_links`:

1. Для нелекционного курса с маркером берётся нормализованная дисциплина.
2. Среди лекционных курсов той же дисциплины выбирается курс с максимальным
   пересечением `group_ids`.
3. Если лучший кандидат один — заполняется `same_room_as_course_id`.
4. Если кандидатов несколько с одинаковым максимумом — связь не задаётся,
   пишется `warning`.
5. Если лекция не найдена — `same_room_as_course_id=null`, пишется `warning`.
6. В `same_room_as_instance_ids` попадают лекционные instances, чьи `group_ids`
   пересекаются с группами курса; если таких нет — все instances лекции.
   При нескольких подходящих instances пишется информационный `warning`.

Если в ячейке одновременно есть «вместе с лекциями» и явные номера
(`вместе с лекциями в комп. классе 334`), сохраняются и `allowed_room_ids`,
и связь с лекцией.

### 15.3. Прочие значения

- `любая`, `аудитория`, `аудиторно`, `онлайн`, `компьютерный класс`, `ИВЦ`,
  корпус/этаж/адрес (`Тургенева 4`, `Куйбышева 48`, `Литер Д`) распознаются как
  общие места: `allowed_room_ids=[]`, без предупреждения о нераспознанном тексте.
- «Компьютерный класс»/`ИВЦ` дополнительно дают `requirements += ["computer_class"]`.
- Текст, который не удалось отнести ни к номерам, ни к общим местам, сохраняется
  в `location_raw` и попадает в `warnings`.

## 16. `venue_type` (п.9 ТЗ)

Тип площадки хранится в `venue_type` на курсе и копируется во все его instances.
Допустимы только четыре значения:

| Значение | Смысл |
|----------|-------|
| `room` | Очное занятие в аудитории/на кампусе |
| `online` | Дистанционный формат |
| `external` | Внешняя организация вне кампуса |
| `unspecified` | Определить не удалось |

Отдельных полей `venue_source`, `ntk_raw`, `delivery_model_raw` нет — сырьё уже
сохраняется в `location_raw`, `comments_raw` и колонках Excel.

### 16.1. Порядок классификации

`_classify_venue` проверяет условия сверху вниз и возвращает первый сработавший тип:

1. `НТК` содержит «онлайн» → `online`.
2. «Модель реализации» содержит «Исключительно ЭО» → `online`.
3. В месте проведения есть онлайн-маркер и **нет** аудиторных маркеров → `online`.
4. В месте есть внешний маркер и нет кампусного адреса → `external`.
5. Место пустое, но комментарий говорит о внешней организации → `external`.
6. Есть `allowed_room_ids` → `room`.
7. Место содержит «вместе с лекциями» / «там же, где и лекции» → `room`.
8. Место содержит аудиторные маркеры (`аудитор`, `класс`, `кабинет`, `лаборатор`,
   `ИВЦ`, `этаж`, `корпус`, `Тургенева`, `Куйбышева`, `Литер` и т.п.) → `room`.
9. Место содержит 3-значный номер аудитории (`153`, `453`) → `room`.
10. Место равно `нет` / `не требуется` / `не проводится` → `unspecified`.
11. `НТК = НК` → `unspecified` + warning.
12. Непустое нераспознанное место → `unspecified` + warning.
13. Иначе → `room` (значение по умолчанию).

Особые случаи:

- `СМУДС (НТК)` **не** считается онлайном: это очно-смешанный формат, поэтому
  строка классифицируется как `room` (или по остальным признакам).
- `ИММ УрО РАН`, `УНИИМ`, `РАН`, `ООО/АО/ПАО/ЗАО`, «на предприятии»,
  «в организации», «обсерватория» — внешние маркеры.
- `Тургенева 4`, `Куйбышева 48`, `Литер Д`, `ИВЦ` — **не** внешние: это кампус.
- Комментарии не переопределяют `venue_type`. Если комментарий говорит об онлайн,
  а тип очный, пишется `venue_conflict:` warning.

## 17. `time_wish_rules` (п.10 ТЗ)

Источник — колонка «Пожелания по времени пар…». Сырой текст всегда сохраняется
в `time_wish_raw`; правила добавляются и на курс, и на instances.

```json
{
  "scope": "teacher",
  "teacher_id": "Перминова О.Е.",
  "soft": false,
  "forbidden_days": ["СУББОТА"],
  "forbidden_slot_ids": [5, 6, 17, 18],
  "min_pair_index": null,
  "max_pair_index": null,
  "day_part": null,
  "max_pairs_per_day": null,
  "source": "Перминова О.Е.: не ставить в субботу, в среду после 15:00"
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `scope` | string | `course` — для всех instances; `teacher` — только для указанного преподавателя |
| `teacher_id` | string \| null | Канонический `Фамилия И.О.` для `scope=teacher` |
| `soft` | bool | `true` — пожелание, `false` — жёсткое ограничение |
| `forbidden_days` | string[] | Запрещённые дни: `ПОНЕДЕЛЬНИК` … `СУББОТА` |
| `forbidden_slot_ids` | int[] | Запрещённые `time_slots[].id` (день + пара) |
| `min_pair_index` | int \| null | Минимальный номер пары (1–6) |
| `max_pair_index` | int \| null | Максимальный номер пары (1–6) |
| `day_part` | string \| null | `morning` (1–3), `afternoon` (4–6), `evening` (5–6) |
| `max_pairs_per_day` | int \| null | Не более N пар в день |
| `source` | string | Фрагмент исходного текста, из которого получено правило |

### 17.1. Алгоритм

1. `time_wish_raw` режется на сегменты по `;`, переводу строки и границе предложения.
2. Внутри сегмента имена преподавателей группируются: `Иванов И.И., Петров П.П.`
   даёт одно правило на каждого; текст после имени относится к этому преподавателю.
3. Полярность определяется по ближайшей подсказке в пределах comma-клаузы:
   `не`, `нельзя`, `кроме`, `исключить`, `запрещено` — запрет;
   `ставить`, `поставить`, `желательно`, `лучше`, `предпочтительно`, `можно` — пожелание.
   Смешанные сегменты разбираются поклаузно.
4. Распознаются:
   - дни недели и сокращения (`пн`, `ср`, `пт`, …);
   - номера пар (`3 пара`, `2-3 пары`, `первая пара`, `не раньше 3 пары`);
   - время (`после 15:00`, `до 12-30`, `с 9:30`) с переводом в номер пары;
   - части дня (`утро`, `первая половина дня`, `после обеда`, `вечер`);
   - `не более N пар в день`.
5. Частотные фразы (`1 пара в неделю`, `по две пары`, `раз в две недели`,
   `через неделю`, `подряд`) не создают ограничений.
6. Положительные ограничения «только день X» / «только пара Y» схема выразить не
   может: они попадают в `time_wish_unmanaged` с причиной `preferred_day`,
   `preferred_day_slot` или `preferred_day_pair`.
7. Если имя преподавателя не найдено среди преподавателей курса, фрагмент уходит
   в unmanaged с причиной `foreign_teacher=[...]`.

`time_wish_unmanaged` — список объектов `{"text": "...", "reason": "..."}`.
Каждый элемент дублируется в `warnings` строкой с префиксом `unmanaged_wish:`.

### 17.2. Привязка к instances

- `scope=course` попадает во все instances курса.
- `scope=teacher` попадает только в instances, где `teacher_id` входит в
  `instance.teacher_ids`.
- `time_wish_unmanaged` копируется во все instances курса.

## 18. `comments_hints` (п.11 ТЗ)

Источник — колонка «Комментарий, особенности дисциплины». Сырой текст всегда
сохраняется в `comments_raw`.

```json
{
  "scope": "лекция",
  "online": true,
  "duration_slots": null,
  "period_start": "2026-09-01",
  "period_end": "2026-10-15",
  "week_ranges": [],
  "semester_half": null,
  "source": "Лекции: в дистанционном формате с 01.09.2026 по 15.10.2026"
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `scope` | string | `all` \| `лекция` \| `практика` \| `лабораторная` |
| `online` | bool | В комментарии есть онлайн/дистанционный формат |
| `duration_slots` | number \| null | Длительность занятия в парах (`4 часа` → `2`) |
| `period_start` | string \| null | Начало периода в ISO `YYYY-MM-DD` |
| `period_end` | string \| null | Конец периода в ISO `YYYY-MM-DD` |
| `week_ranges` | int[][] | Пары `[начало, конец]` недель |
| `semester_half` | int \| null | `1` или `2` — половина семестра |
| `source` | string | Фрагмент комментария |

### 18.1. Эвристики

- «4 часа» → `duration_slots = 2`; «полторы пары»/`1,5 пары` → `1.5`;
  «сдвоенные», «две пары подряд», «без окна» → `2`.
- `с 01.09.2026 по 15.10.2026` → `period_start` / `period_end` в ISO.
- `с 2 по 5 недели`, `2-5 недели`, `недели 2-5, 16 и 8-11` → `week_ranges`.
- «первая/вторая половина семестра» → `semester_half`.
- `scope` определяется по словам «лекции», «практические», «лабораторные»;
  если тип не назван — `all`.
- В instance попадают только hints с `scope=all` или `scope`, совпадающим с
  `lesson_type` курса.

Комментарии **не** меняют `venue_type` и не удаляют комнаты. Онлайн-намёк при
очном `venue_type` даёт `venue_conflict:` warning. Извлечённые эвристики также
пишутся в `warnings` с префиксом `comments_hint:`.

## 19. `fixed_schedules` (п.12 ТЗ)

Верхнеуровневый массив в итоговом JSON:

```json
"fixed_schedules": [
  {"course_id": "c1",  "timeslots_ids": [11, 19]},
  {"course_id": "c18", "timeslots_ids": [17, 25]},
  {"course_id": "c46", "timeslots_ids": [1, 35]}
]
```

Запись создаётся для каждого курса с именем из `fixed_course_names`
(«Прикладная физическая культура (практика)»).

### 19.1. Источник слотов

`_parse_pe_slots` читает лист «Физ.культура»:

1. Находит строку заголовка с «День недели» и «Пара».
2. Находит колонку института (`ИЕНиМ`) в заголовке или следующей строке.
3. Идёт по строкам после заголовка; запоминает текущий день по первой колонке.
4. Для непустой ячейки института берёт год обучения и номер пары и переводит их
   в `time_slots[].id` через `(день, номер пары)`.
5. Один и тот же слот не может встретиться дважды для одного года.

Год обучения берётся из служебного `_course_number` курса (колонка «Курс»).
Если для года нет слотов или год не определяется — `ParserValidationError`.

### 19.2. Валидация

`_validate_fixed_schedules` вызывается до возврата JSON и проверяет:

- `time_slots` непуст, `id` — целые числа `1..N` без пропусков и дублей;
- пары `(day, slot_index)` уникальны, день входит в `self.days`;
- `course_id` существует и является фиксируемым курсом;
- записей ровно по одной на каждый фиксируемый курс, без лишних;
- `timeslots_ids` — непустой список целых чисел без дублей;
- каждый `timeslot_id` существует в `time_slots`.

Любое нарушение — `ParserValidationError(ValueError)`, а не `warning`.
Невалидные слоты (например, старый хардкод `40` при 36 слотах) **не отбрасываются
молча**: парсер падает до передачи данных солверу.

## 20. Часы → занятия и `week_pattern` (п.16 ТЗ)

Правила читаются из `parser/config.json` и глубоко сливаются с дефолтами
`DEFAULT_PARSER_CONFIG` в `Importer._load_config`. Конструктор принимает
`config` (dict или путь к JSON) и `parse_room_occupancy`.

Поля `hours_per_semester` и `hours_rule` из курса и instances **удалены**.
Вместо них выставляются:

- `lessons_per_week` — сколько занятий в неделю;
- `week_pattern` — `weekly`, `odd` или `even`;
- `duration_slots` — длительность занятия в слотах.

### 20.1. Порядок выбора правила

1. `hours` отсутствует или `<= 0` → курс не создаётся, счётчик пропусков
   увеличивается; после обхода листов выводится агрегированное предупреждение
   `Лист '<sheet>': «<колонка>» пусто / = 0 в N строках — курсы не созданы`.
2. Точное значение в `hours.exact`.
3. `0 < hours < 16` → `hours.below_16_policy` (по умолчанию `biweekly`).
4. Диапазон из `hours.ranges` (включительно).
5. Резерв: `max(1, ceil(hours / hours.unit_hours))`, `week_pattern="weekly"`.

Для `biweekly` parities раздаются round-robin (`hours.biweekly_start`,
по умолчанию `odd`), поэтому чётные и нечётные недели заполняются равномерно.
Итоговый `week_pattern` никогда не остаётся `biweekly`: в JSON попадает
`odd` или `even`.

| Часы | `lessons_per_week` | `week_pattern` |
|------|--------------------|----------------|
| 0 / пусто | — курс не создаётся | — |
| 1–15 | 1 | `odd` / `even` |
| 16 | 1 | `odd` / `even` |
| 17–31 | 1 | `weekly` |
| 32 | 1 | `weekly` |
| 33–47 | 2 | `weekly` |
| 48 | 2 | `weekly` |
| 49–63 | 2 | `weekly` |
| 64 | 2 | `weekly` |
| 65–96 | 3 | `weekly` |
| 97–128 | 4 | `weekly` |
| > 128 | `ceil(hours / 32)` | `weekly` |

### 20.2. `duration_slots`

По умолчанию `1`. Для `lesson_type="лабораторная"` берётся максимум
`comments_hints[].duration_slots` среди hints со `scope=all|лабораторная`.
Поведение управляется `hours.long_lab`:

```json
"long_lab": {"use_comment_hint": true, "default_duration_slots": 1}
```

Все instances курса получают те же `lessons_per_week`, `week_pattern` и
`duration_slots`, что и курс.

## 21. Сессия и отчётные мероприятия (п.13 ТЗ)

Сессионные колонки (`Зачет / экзамен`, ФИО принимающего, вид, время,
консультация, свободные дни, аудитория, особенности, даты, ограничения,
примечание) **не участвуют** в недельных курсах, instances, связях анкет и
`fixed_schedules`.

В итоговом JSON они выносятся отдельно:

```json
"ignored": {
  "session_requests": [
    {
      "id": "s6",
      "sheet": "Тургенева 4 по выбору",
      "course_ids": ["c1153", "c1154"],
      "discipline": "Асимптотические методы",
      "group_ids": ["МЕН-340101", "МЕН-340102"],
      "report_type": "зачет",
      "teacher_name": "Ершов А.А.",
      "report_format": "письменный",
      "time_window_raw": "10:40-12:20",
      "consultation_raw": "нет",
      "free_days_min": 4,
      "room_requirement_raw": "обычная",
      "scope_raw": "весь поток",
      "date_windows": [
        {"start": "2026-12-26", "end": "2026-12-26", "raw": "26.12.26"}
      ],
      "restrictions_raw": "не ставить с 9:00",
      "note_raw": null
    }
  ]
}
```

- Лист считается «сессионным», только если в нём есть расширенные колонки
  отчётных мероприятий. Одна колонка `Зачет / экзамен` на обычных листах
  (`ХИМИКИ`, `ФИНЗ`, `ЭБМ` и т.п.) сессией не считается.
- Запрос создаётся, если непусто хотя бы одно сессионное поле.
- Дубликаты убираются по полному набору сессионных полей.
- `course_ids` ссылается на недельные курсы той же строки; если их нет —
  пустой список.
- Включение/выключение блока — `session.enabled` в конфиге.

## 22. Сетка слотов и 7-я пара (п.14 ТЗ)

`_parse_teachers_desires` маппит номер пары из заголовка анкеты на
`time_slots` по ключу `(день, номер пары)`. Если слота нет, значение не
теряется молча:

- `pair_grid.unsupported_pair_policy="warn"` (по умолчанию) добавляет
  warning ровно с текстом
  `7-я пара игнорируется: слот отсутствует в сетке`;
- `"error"` → `ParserValidationError` с днём и номером пары.

Слот в `timeslots_ids` не добавляется: текущая сетка содержит 6 пар в день.

## 23. Предзаполненная занятость аудиторий (п.15 ТЗ)

Управляется только параметром конструктора:

```python
Importer(parse_room_occupancy=True)
```

- По умолчанию `False`: текст эталонного расписания в ячейках листа
  «Аудитории» игнорируется, `room_preblocked: []`.
- При `True`: каждая непустая ячейка слота превращается в запись
  `{"slot_id": <int>, "room_id": "<id>"}`.
- `slot_id` берётся из `time_slots`, `room_id` — из колонки «Ауд.».
- Записи дедуплицируются; неизвестные аудитории/слоты пропускаются с warning.
- На текущем файле — 1737 записей, все ссылки валидны.

```json
"room_preblocked": [
  {"slot_id": 2, "room_id": "204"},
  {"slot_id": 3, "room_id": "204"}
]
```

## 24. Курсы без преподавателя (п.17 ТЗ)

Политика применяется после канонизации ФИО и связывания анкет, но до
`_finalize_course_instances`, чтобы placeholder успел попасть в `teachers[]`.
Настройки — `missing_teacher` в `parser/config.json`.

### 24.1. Белый список

Отсутствие преподавателя допустимо, если выполняется любое условие:

- `venue_type` в `whitelist.venue_types` (по умолчанию `online`, `external`);
- `<discipline> (<lesson_type>)` в `whitelist.course_names`
  (по умолчанию `Прикладная физическая культура (практика)`);
- `lesson_type` в `whitelist.lesson_types` (по умолчанию пусто).

У таких курсов `teacher_ids` остаётся пустым списком.

### 24.2. `soft` (по умолчанию)

Для каждого оставшегося курса:

- `teacher_ids = ["UNKNOWN:<course_id>"]`;
- все instances получают тот же placeholder;
- placeholder добавляется в `teachers[]`;
- пишется warning
  `Курс <id> (<discipline> (<lesson_type>)): нет преподавателя; назначен UNKNOWN:<id>`.

### 24.3. `strict`

Парсер не возвращает JSON и бросает `ParserValidationError` со списком
проблемных курсов: `id`, `<discipline> (<lesson_type>)`, `venue_type`.
